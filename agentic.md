# Agentic Architecture: Chandas-Aware Sanskrit TTS Pipeline

Companion to `rules.md`. That file defines *what is true* about a verse (syllables, weight, meter, yati). This file defines *what computes it, what an LLM is trusted to decide, and how the result becomes a prompt Gemini TTS can act on*.

## Grounding assumption about Gemini TTS (verify against current docs before building)

Gemini TTS takes two things per call: a **transcript** (the literal text to speak) and a **style/direction prompt** (natural language describing accent, pace, tone, emotion — e.g. "speak slowly and reverently, pausing briefly at each phrase break"), plus optional inline delivery tags like `[whispers]`. It does **not** accept SSML-style per-phoneme duration/pitch control as its primary interface — the control surface is prose instructions, not structured markup. This has one direct architectural consequence: **your deterministic syllable-level annotations (L/G, yati, mātrā duration) cannot be handed to Gemini TTS as-is.** Something has to compress a syllable-by-syllable analysis into a small number of natural-language directives a language model can actually execute — that compression step is the one genuinely "agentic" (judgment-requiring) part of this whole pipeline. Everything upstream of it should be deterministic code, not an LLM call, precisely because you already did the hard work of making it rule-based in `rules.md`.

---

## 0. Core design principle

**Only two things in this system should touch an LLM:**
1. **Disambiguation** — cases where the deterministic rules genuinely can't decide (sandhi-split ambiguity, competing meter matches, vipulā classification).
2. **Composition** — turning a structured, already-correct prosody annotation into fluent natural-language TTS direction.

Everything else (syllabification, weight, meter matching, yati lookup) is **pure deterministic code from `rules.md`**, called as tools, never regenerated by an LLM. If an LLM is ever asked "is this syllable guru or laghu," that's a design bug — the rules are not probabilistic, don't spend model capacity re-deriving them, and don't let an LLM silently overrule a computed answer.

## 1. Pipeline overview

```
Raw verse text
     │
     ▼
[0] Ingestion & Chunking Tool  (deterministic)
     │
     ▼
[1] Syllabifier Tool           (deterministic — rules.md §2)
     │
     ▼
[2] Weight Classifier Tool     (deterministic — rules.md §3)
     │
     ▼
[3] Meter Matcher Tool         (deterministic — rules.md §4)
     │             │
     │        low confidence / tie
     │             ▼
     │      [3a] Meter Disambiguation Agent (LLM, narrow scope)
     │             │
     ◄─────────────┘
     ▼
[4] Yati Resolver Tool         (deterministic lookup — rules.md §5)
     │
     ▼
[5] Chant-Rule Annotator       (mostly deterministic; LLM-assisted for
     │                          compound-boundary detection — rules.md §6)
     ▼
ProsodyAnnotation (structured, per-syllable + per-pada object)
     │
     ▼
[6] Prosody-to-Prompt Composer Agent (LLM — the main generative step)
     │
     ▼
{ transcript_chunk, style_prompt, tags_used, style_state }
     │
     ▼
[7] Gemini TTS call
     │
     ▼
[8] (optional, Phase 2) Audio QA / Feedback Agent
```

Stages 0–4 map directly onto `rules.md` Sections 2–5 — implement them as pure functions with unit tests against a golden verse corpus, not as prompts. Stage 5 is mostly deterministic but has one genuinely hard sub-problem (see below). Stage 6 is where the agentic system earns its keep.

## 2. Component specification

### [0] Ingestion & Chunking Tool (deterministic)
- Normalize (rules.md §0), detect script, split text into **verses**, then **pādas** (natural chunk unit for TTS — matches yati/breath structure).
- Retain word-boundary and compound-boundary offsets as metadata alongside the phoneme stream (needed by Stage 5), even though Stages 1–4 ignore them.
- Output: `VerseUnit { id, padas: [{ text, word_spans[], compound_spans[] }] }`

### [1]–[4] Deterministic tools
Implement exactly as specified in `rules.md`. No agent involvement. Each should:
- Take structured input, return structured output + a `rule_applied` / `confidence` field per decision (already specified in rules.md §7's `WeightedAkshara`).
- Be independently unit-testable against a hand-verified corpus (see §5 below).
- Never call an LLM internally. If they can't resolve something, they return a `needs_disambiguation: true` flag and hand off — they don't guess.

### [3a] Meter Disambiguation Agent (LLM — narrow, constrained)
Invoked **only** when the Meter Matcher returns:
- multiple candidate meters within edit-distance tolerance of the observed L/G string, or
- an Anuṣṭubh pattern that deviates from pathyā at more than the tolerated positions (candidate vipulā vs. genuine scansion error vs. transcription error upstream).

**Scope restriction:** this agent receives only the computed L/G string, syllable count, and candidate meter names with their canonical patterns — not the raw verse semantics. Its job is classification among a closed set of options, not free interpretation. It must return one of: `{chosen_meter, "irregular/vipulā", "likely_input_error"}` with a rationale string logged for audit. If it can't confidently choose, it defaults to `"unclassified"` rather than guessing — an unclassified verse should not silently get a default meter's yati/prosody applied.

### [5] Chant-Rule Annotator (hybrid)
- Daṇḍa/dvidaṇḍa pause insertion: deterministic (they're literal characters in the text).
- Visarga/vowel-continuity handling: deterministic (rules.md §6).
- **Compound-boundary detection (where NOT to breathe)**: this is a genuinely hard Sanskrit NLP problem (compound segmentation is not fully solved by rule-based methods). Use the word/compound-span metadata retained in Stage 0 if the source text is already segmented (e.g. from a padapāṭha or a tagged corpus). If the input is continuous saṃhitā-style text with unmarked compounds, this is a legitimate place for a constrained LLM call — given the pāda text, identify likely compound boundaries — but treat its output as a **suggestion with confidence**, not ground truth, since a wrong compound boundary only affects breath-pause placement, not meter correctness (a low-stakes place to tolerate LLM uncertainty, unlike Stages 1–4).

### [6] Prosody-to-Prompt Composer Agent (LLM — the core agentic step)
**Input:** one `ProsodyAnnotation` object per pāda/verse chunk (per rules.md §7), containing: syllable sequence, per-syllable weight + duration hint, yati positions + strength, meter name, chant-rule pause markers, and a **style_state** carried from the previous chunk (see §3 below).

**Output (structured, not free text):**
```json
{
  "transcript_chunk": "<clean text to speak, exactly as-is — the Composer must not alter Sanskrit spelling/content>",
  "style_prompt": "<natural language direction for Gemini TTS>",
  "tags_used": ["[pause]", ...],   // only from an allow-listed tag set
  "style_state": { "register": "...", "pace": "...", "carried_forward_notes": "..." }
}
```

**Critical constraint — templated backbone, not free generation:**
Don't let the LLM invent the style prompt from scratch each time; that reintroduces the non-determinism you spent five layers eliminating. Structure the Composer as:
1. A **deterministic template** fills in the facts that must not drift: meter name, yati position/strength, count of guru syllables in a row (long guru runs → explicit slow-down instruction), presence of visarga/anusvāra-heavy endings, chant-rule pause count.
2. The **LLM's only job** is to phrase those facts fluently and consistently as a single coherent style prompt, and to decide relative emphasis wording (e.g. "with steady reverence" vs "briskly") — never to add or omit a pause position, never to change which syllables are marked heavy.
3. Validate the LLM output against the input facts before sending to TTS: e.g. if `yati_positions` has 2 entries, the style prompt should reference 2 pause cues — a simple regex/keyword check on the composer's output catches silent omissions.

**Example composer prompt (system message, abbreviated):**
```
You are writing a short performance direction for a Sanskrit TTS engine.
You will be given: meter name, syllable weights, yati (pause) positions,
and chant rules for one verse-line. Do not alter the transcript text.
Do not invent pause positions or weights not given to you.
Write ONE natural-language style instruction (2-3 sentences) that a
voice actor could follow, covering: overall pace/register, where to
pause and how long, and where to lengthen/stress syllables (long runs
of guru syllables = slow down and lengthen).

Facts:
  meter: Vasantatilakā
  yati: after syllable 8 (obligatory)
  guru_runs: syllables 9-11 (three consecutive guru)
  ends_in_visarga: true

Transcript: <pāda text>
```
This keeps the "creative writing" surface area small and auditable — you can literally diff the facts against the output prompt in a test.

### [7] Gemini TTS call
- One call per chunk (pāda or verse, tune based on latency/length limits — verify current input-length guidance before deciding chunk granularity).
- Carry `style_state` forward between calls in the same chant so consecutive verses don't drift in pace/register — pass the previous chunk's realized style summary as context in the next Composer call, not as raw audio.

### [8] Audio QA / Feedback Agent (optional, Phase 2)
If you have an ASR or forced-alignment step available: transcribe the generated audio back, compare pause timing against `yati_positions`, and flag chunks where the realized pause is absent or misplaced, feeding back into a retry with an adjusted style prompt. Treat this as an enhancement, not a blocker for v1 — don't let a heavier audio-verification loop delay shipping the deterministic core.

## 3. Orchestration pattern

Use a **linear state-machine orchestrator** (e.g. a simple Python pipeline or a LangGraph-style DAG with two conditional branches for Stages 3a and 5's LLM fallback), not a free-form multi-agent chat. Reasons:
- Determinism and testability matter more here than flexibility — you're not solving an open-ended task, you're running a fixed pipeline with two narrow judgment calls.
- Every stage boundary is a place to insert a unit test with the golden corpus from `rules.md` §7's data contract.
- A supervisor-agent-picks-the-next-step pattern adds latency and non-determinism for zero benefit when the control flow is already known.

Recommended state object carried through the whole pipeline (extends rules.md §7):
```
PipelineState := {
  verse_id, raw_text,
  akshara[]: WeightedAkshara,
  meter_match: MeterMatch,
  disambiguation_log: [ {stage, input, decision, rationale} ],  # audit trail
  prosody_annotation: ProsodyAnnotation,
  composer_output: { transcript_chunk, style_prompt, tags_used, style_state },
  style_state_carry: {...}   # passed to next verse's Composer call
}
```
Keep `disambiguation_log` non-optional — any time an LLM made a judgment call anywhere in the pipeline, it should be reconstructable later, both for debugging misclassified verses and for building your eval set.

## 4. Guardrails specific to the agentic components

- **Allow-list inline tags.** Only pass tags to Gemini TTS that you've confirmed it supports (verify current tag set in docs before hardcoding). Reject/strip anything the Composer invents outside that list.
- **Composer must echo the transcript unchanged.** Diff `transcript_chunk` against the ingested pāda text before sending to TTS; any mismatch is a bug (the Composer rewriting Sanskrit text, however slightly, is exactly what will silently corrupt sandhi/meter).
- **Fact-check the style prompt against the annotation**, as described in Stage 6 — cheap, mechanical, catches the main failure mode (LLM dropping a pause instruction or misdescribing which syllables are heavy).
- **Confidence thresholds gate everything**, not just Stage 3a: if Stage 2/3 confidence is low for reasons other than the two named disambiguation cases, halt and surface to a human reviewer rather than pushing a guess downstream to the Composer, which would then confidently narrate an incorrect prosody.

## 5. Testing & evaluation strategy

1. **Golden corpus**: 30–50 verses across several meters (Anuṣṭubh, a couple of samavṛttas, at least one with genuine vipulā or edge-case sandhi) with hand-verified syllable/weight/meter/yati annotations. Unit-test Stages 1–4 against this before writing a single Composer prompt.
2. **Composer regression set**: for a fixed set of `ProsodyAnnotation` inputs, store expected *facts* (not exact wording) the style prompt must contain — pause count, pace direction, which syllables get lengthening cues — and assert on those, not on exact string match (LLM phrasing will vary run to run; the facts shouldn't).
3. **Audit trail review**: periodically sample `disambiguation_log` entries to check the Stage 3a/5 LLM's judgment calls are actually sound — this is your signal for whether the narrow-scope agents need better prompts or more constrained input.
4. **End-to-end listening review**: have someone who reads Sanskrit prosody listen to a sample of final audio against the intended yati/weight pattern before scaling up volume.

---

## 6. What NOT to build (scope discipline)

- Don't let any agent "learn" or override meter tables — if a verse doesn't match, that's signal to fix the meter table or flag the verse, not to have an LLM force-fit it.
- Don't feed the Composer the full verse's semantic meaning/translation unless devotional tone genuinely depends on content (e.g., a verse addressed to a deity vs. a philosophical śloka might warrant different register) — if you do, treat that as a separate, explicit input field (`semantic_register: "devotional"|"narrative"|"philosophical"`) rather than letting the LLM infer tone from raw meaning, so it stays auditable.
- Don't SSML-ify internally and then hope Gemini TTS interprets it — if its primary interface is natural language + a small tag set, design Stage 6's output format to match that reality rather than building an internal representation that has to be translated twice.
